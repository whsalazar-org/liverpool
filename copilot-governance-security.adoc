= GitHub Copilot governance and security: a developer's guide
:toc:

Source review date: 14 October 2026.

This guide is for developers using Copilot suggestions, chat, code review, local agents, or the cloud agent. It explains everyday decisions, not enterprise administration. Features, defaults, and availability change by plan, client, model, and organization policy; check the linked documentation before relying on a control.

*Bottom line:* Copilot is an assistant, not a security boundary or an accountable reviewer. You remain responsible for the code, data, and actions you accept.

== 1. Governance in your daily workflow

Governance means deciding where AI is allowed, what information it may use, what actions it may take, and who verifies the result.

* *Your organization or repository owners* set applicable policies, feature/model access, content exclusions, repository access, and merge requirements. Some settings are inherited and cannot be changed by individual developers.
* *You* use the approved account and tools, minimize shared context, approve only necessary actions, inspect changes, and follow normal review and incident processes.
* *Maintainers and reviewers* enforce the repository's required checks and approvals. Copilot assistance is not a reason to bypass these gates.

Before using Copilot on work code, confirm which account and subscription are active, whether the repository and data classification permit that use, and which models and integrations are approved. If a feature is unavailable or a policy seems wrong, ask the repository owner or security team rather than switching to a personal account to evade it. See <<policies>> and <<mcp>>.

== 2. Protect inputs and understand privacy

Copilot processes prompts and contextual information, not just text you deliberately paste. Context can include code, attached files, conversation history, and tool results, depending on the feature. Review what you attach or let an agent read. See <<agents>>.

* Do not submit passwords, tokens, private keys, production credentials, or customer/personal data unless your organization's explicitly approved process permits the data involved. Prefer synthetic examples and redacted logs.
* Share the smallest useful code fragment. Remove sensitive identifiers and payloads from stack traces, screenshots, and bug reports.
* Do not treat a private repository, `.gitignore`, or a prompt saying "do not read secrets" as a guarantee that Copilot cannot access or transmit information.
* Treat chat history, session logs, and shared agent sessions as potential copies of sensitive context. Follow your organization's retention and sharing rules.

=== Training is not the same as retention

GitHub states that Copilot Business and Enterprise customer data is not used to train AI models. For individual plans (Free, Pro, Pro+, and Max), GitHub's documentation says that, starting 24 April 2026, interactions may be used for model training and improvement unless you opt out. In your GitHub *Copilot settings*, set *Allow GitHub to use my data for AI model training* to *Disabled* if appropriate. Verify your active plan; this setting is not shown for Business or Enterprise licenses. See <<policies>>.

An opt-out or a no-training commitment does *not* mean no processing, no storage, or no third-party involvement. Model hosting, caching, retention, preview exceptions, and integration data flows differ. Consult <<hosting>> and the applicable privacy terms, and ask your security team before sending restricted information. Do not assume one model provider's zero-data-retention arrangement applies to all Copilot features.

== 3. Security features and their limits

[cols="1,2,2",options="header"]
|===
|Feature |What it provides |What you still need to do

|Organization policies
|Controls over available features, models, and integrations, depending on subscription and surface.
|Use the approved identity and workflow; do not assume a personal subscription inherits organization controls. See <<policies>> and <<mcp>>.

|Content exclusion
|Business/Enterprise controls that exclude configured content from supported suggestions, chat, and code review.
|Verify support for your exact client and mode. Exclusion is not a universal data-loss-prevention boundary. See <<exclusion>>.

|Public-code matching and references
|Supported products can block matching suggestions or show references to matching public code.
|Check references and licenses; a missing match is not proof of originality or permission to use the code. See <<policies>> and <<github-surface>>.

|Content filters
|Checks intended to detect certain harmful or offensive content, with public-code checks where applicable.
|Review output for correctness and security; filtering does not guarantee secure code. See <<hosting>> and <<agents>>.

|Agent permissions and isolation
|Local tool permission controls; the cloud agent uses an ephemeral environment with a firewall enabled by default.
|Review the actual permissions, configuration, commands, and destinations. Local agents do not automatically inherit cloud isolation. See <<cli>>, <<agents>>, and <<cloud-risks>>.

|Cloud-agent validation
|By default, code review, CodeQL, secret scanning, and checks of new dependencies against relevant GitHub advisories.
|Inspect session results and run repository checks. Tools can be disabled and coverage is limited; these are not a security certification. See <<cloud-risks>>.
|===

=== Content exclusion: check the surface, not just the file

GitHub documents that content exclusion is not supported in Copilot Chat *Edit and Agent modes* in VS Code and other editors. Current support tables list CLI support, while the exclusion configuration guide still says CLI is unsupported. Confirm behavior for your deployed client and policy with your security team rather than relying on either statement alone. GitHub also documents indirect semantic-context leakage, such as type information supplied by an IDE, and limitations for symlinks and remote filesystems. Consult the current support table for the feature you actually use, including GitHub.com experiences. See <<exclusion>>, <<policy-surfaces>>, and <<exclusion-setup>>.

If information must never leave an approved boundary, keep it outside the agent's accessible environment and use your organization's approved access controls. Do not paste excluded content into a prompt or expose it through a tool and expect a file-based rule to protect that copy.

=== Public-code references: a review aid, not license clearance

Where configurable, the *Suggestions matching public code* setting offers *Allow* or *Block*. An organization-assigned setting may be inherited. Blocking is supported in most, not all, products; the policy matrix lists cloud-agent matching as annotate-only. On GitHub.com, code references search an index of public GitHub repositories, not private repositories or code hosted elsewhere, and that index can be incomplete or out of date. See <<policies>>, <<policy-surfaces>>, and <<github-surface>>.

When a reference appears, inspect the source and license, follow your team's attribution and dependency policy, and ask for legal guidance when uncertain. The absence of a reference does not eliminate intellectual-property obligations.

== 4. Use agents and external tools with least privilege

Agentic features can edit files, execute commands, and call external services. A shell command can exercise your user account's capabilities, including deleting files or making network requests. See <<cli>>.

* Start with a small, explicit task on a separate branch. Define allowed scope, expected tests, and actions that need human approval.
* Keep permission prompts enabled where supported. Read the complete command, working directory, file paths, and network destinations before approving it; watch for chained commands and scripts downloaded from the internet.
* Avoid broad persistent approvals and CLI `--allow-all`/`--yolo` on normal development machines. GitHub recommends permissive options only in isolated environments. Review and revoke saved permissions when no longer needed.
* Use an appropriately isolated environment for unfamiliar repositories or risky tasks. A separate branch protects review history, not the rest of your machine or credentials.
* Connect only approved Model Context Protocol (MCP) servers. MCP connects Copilot to additional tools and data; it is not a trust certification. Review the server publisher, configuration, accessible data, enabled tools, and authentication scopes. Prefer read-only access and short-lived, narrowly scoped credentials.
* Treat data sent to external tools, web search, or integrations as an additional disclosure path. Verify the destination and applicable policy before enabling them.

See <<cli>> and <<mcp>> for product controls and current configuration details.

*Cloud-agent exception:* configured MCP tools are used autonomously without per-call approval. Review the allowed toolset and credentials before starting work, not just when a permission prompt appears. The default GitHub MCP token is read-only and scoped to the current repository, but configuration can broaden that access. See <<cloud-mcp>>.

=== Prompt injection: untrusted content can become instructions

Prompt injection occurs when malicious input tries to redirect an AI assistant. Indirect injection can arrive through a repository file, issue, web page, or tool response that the assistant reads. GitHub documents this risk and cloud-agent mitigations; OWASP explains the wider threat in <<owasp>>.

For example, a dependency README could tell an agent to upload environment variables to a "diagnostic" endpoint. That is untrusted content, not authorization. Reject the command, stop the session if needed, and report the suspicious material. Custom instructions such as "never reveal secrets" help communicate intent but do not enforce access control or prevent every injection.

Limit accessible secrets and tools before the task starts. Do not disable approvals or expand network access merely because text encountered by the agent requests it.

=== Cloud-agent work still needs human review

GitHub's documented mitigations include restricted branch writes, branch protections and required checks, an outbound firewall, and human review before merging agent-created draft pull requests. The agent cannot approve or merge a pull request. By default, Actions workflows on its changes require a user with write access to approve execution; automatic workflow execution can be configured. See <<cloud-risks>>.

Before approving workflows, review the entire diff, especially workflow files, install scripts, dependency changes, and code that could access CI credentials. Do not add production secrets to an agent environment or broaden its network access just to make a task pass. Review session logs to understand tools used and validation performed, without assuming that every possible vulnerability was checked.

The cloud firewall is not comprehensive: it applies to processes started through the agent's Bash tool, not directly to MCP server processes or configured setup steps. Isolation and an allowlist therefore do not eliminate every exfiltration path. See <<firewall>>.

== 5. Validate generated code like any other contribution

Copilot can produce plausible but incorrect code, miss vulnerabilities, invent APIs or packages, and give mistaken review feedback. Copilot code review supplements rather than replaces human review. See <<agents>>.

. Read the entire diff and confirm that each change is needed. Pay particular attention to authentication, authorization, input handling, SQL/command injection, cryptography, and logging of sensitive data.
. Verify API behavior against official documentation. Check dependency names, provenance, licenses, and security advisories before installing; do not install a package solely because Copilot suggested it.
. Run the repository's existing formatting, lint, build, and test checks. Add focused tests for changed behavior, including invalid inputs, denied permissions, and regression cases. Independently assess generated tests; they can repeat the implementation's mistake.
. Use available repository security checks, such as secret scanning, dependency review, and code scanning. These are complementary GitHub capabilities, not automatically provided everywhere you use Copilot; availability and configuration vary.
. Obtain the required human review and checks before merging. Explain consequential AI-assisted decisions in the pull request according to team policy, and include what was tested and any limitations.

Do not accept changes to disable security checks, weaken validation, or expose credentials just to resolve an error.

== 6. Quick checklist and incident response

*Before a session*

* Confirm approved account, repository, model, and integrations.
* Minimize context and remove sensitive data.
* Verify content-exclusion support and actual tool permissions.

*Before accepting or merging*

* Inspect commands, destinations, the full diff, and any public-code references.
* Run relevant tests and security checks; review their results.
* Get the required human approval and preserve useful review evidence without copying secrets into it.

*If something goes wrong*

Stop the agent or tool execution and revoke unnecessary access. If a credential was exposed, revoke or rotate it through your normal incident process; deleting a chat message or reverting a commit is not sufficient. Notify your security team or repository owner, record the affected systems and actions without reproducing the secret, and follow their instructions for log handling and remediation.
